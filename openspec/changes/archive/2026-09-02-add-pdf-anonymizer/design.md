## Контекст

См. `proposal.md` — раздел «Зачем» — для мотивации. Здесь только то, что
нужно для объяснения технического подхода.

Действующие ограничения проекта, влияющие на дизайн:
- `PIIDetector` (`detection/`) — синхронный, принимает произвольный текст и
  возвращает `DetectionResult` со списком `PIISpan` (офсеты в переданном
  тексте). Он не знает про PDF, координаты или страницы — и не должен
  узнавать: вся PDF-специфика остаётся в новом подпакете `pdf/`.
  `ContextualValidator` внутри `PIIDetector` использует lookback в
  `CONTEXT_LOOKBACK_WORDS = 3` слова для разрешения PER/LOC — значит на
  вход ему нужен связный текст, а не обрубки в 1-2 слова.
- `Natasha` в `detection/natasha_ner.py` уже реализует паттерн graceful
  degradation: `is_available = False` при сбое загрузки модели вместо
  исключения. Тот же паттерн переиспользуется для отсутствующих PDF/OCR
  зависимостей.
- `AuditLogger` логирует только типы и количества сущностей, никогда сами
  значения — это жёсткий инвариант проекта (README, раздел
  «Безопасность»). Новый подпакет обязан ему соответствовать: `stats`
  результата обезличивания PDF не должен содержать исходных значений PII.

## Цели / Не-цели

**Цели:**
- Обезличивание PII в PDF с текстовым слоем и в сканах (через OCR) одним
  публичным API.
- Редакция необратима: PII физически удаляется из содержимого файла, а не
  только скрывается визуально.
- Переиспользование существующего `PIIDetector` без изменений в нём.
- Базовый пакет (`privacyguard_pipeline` без extra `pdf`) продолжает
  работать и импортироваться как раньше.

**Не-цели:**
- Редактируемость/аннотирование PDF помимо редакции (подписи, формы,
  штампы) — не в скоупе.
- Поддержка форматов, отличных от PDF (DOCX, изображения как отдельные
  файлы) — не в скоупе этой фичи.
- Асинхронный API для PDF-обезличивания — `PDFAnonymizer.anonymize()`
  синхронный, в отличие от `PrivacyGuardPipeline.process()`; PyMuPDF и
  Tesseract — блокирующие C-биндинги, оборачивание в `async` ничего не даёт
  без вынесения в отдельный поток/процесс, что оставлено на будущее при
  необходимости.
- Точная настройка качества OCR (PSM-режимы Tesseract, препроцессинг
  изображений) — не в скоупе первой итерации, см. «Открытые вопросы».

## Решения

### 1. Извлечение текста на уровне строки/блока, а не span'а
`page.get_text("dict")` отдаёт font-run span'ы — слишком мелкую единицу для
детекции (см. Explore-обсуждение: контекст для NER и ContextualValidator
теряется, PII, разбитый между span'ами, пропускается). Вместо этого
`text_extractor.py` собирает текст на уровне `line` (в терминах того же
`get_text("dict")`), склеивая span'ы построчно, и параллельно строит карту
"офсет символа в склеенной строке → bbox слова", используя
`page.get_text("words")` для точных границ слов. `PIIDetector.detect()`
вызывается один раз на строку (либо на блок, если строки короткие и нужен
больший контекст — решается эмпирически при реализации, не меняет контракт
спека).

Альтернатива — собирать текст на уровне всей страницы целиком — даёт ещё
больше контекста для NER, но усложняет офсет-маппинг (нужно аккуратно
учитывать переносы строк/абзацев, которые PyMuPDF не гарантирует как
whitespace в исходном порядке чтения) и увеличивает "радиус поражения"
случайной ошибки маппинга. Строка/блок — компромисс, достаточный для
контекстной эвристики (окно в 3 слова) без сложностей полностраничного
reflow.

### 2. Настоящая редакция вместо визуального прямоугольника — на уровне span'а, с восстановлением текста
`page.add_redact_annot(bbox)` + `page.apply_redactions(images=fitz.PDF_REDACT_IMAGE_PIXELS)`
вместо `page.draw_rect(fill=...)` (черновик `feature.md`) — отклонён:
PII остаётся извлекаемой из content stream, что нарушает инвариант
безопасности проекта. Для сканов `images=PDF_REDACT_IMAGE_PIXELS`
дополнительно закрашивает пиксели растра под прямоугольником, так что
`redact_page_boxes` (`renderer.py`) — один и тот же код для OCR-пути,
без отдельной ветки редакции для сканов.

Для текстового слоя `apply_redactions` пришлось усложнить: **эмпирически
обнаружено** (при проверке на реальном документе, не в синтетических
тестах), что `apply_redactions` удаляет текст на уровне PDF-"span" —
непрерывного однородного по шрифту участка в content stream (типично —
вся строка целиком у документов с выравниванием по ширине, где
генератор PDF пишет строку одним `TJ`-оператором). Прямоугольник
редакции даже по одному слову приводил к тому, что MuPDF стирал весь
span целиком — то есть соседний, не-PII текст на той же строке исчезал
без всякого прямоугольника над ним.

Финальная реализация (`renderer.redact_text_layer`) для текстового слоя:
1. Каждое совпавшее PII-слово через `_find_span_for_word` сопоставляется
   с PDF-span'ом (`page.get_text("dict")`), которому принадлежит.
2. Редактируется **весь span целиком**, **без заливки** (`add_redact_annot(rect)`
   без `fill=`) — заливка спрятала бы восстановленный текст под чёрным.
3. До вызова `apply_redactions()` (важен порядок: после редакции PyMuPDF
   может убрать из страницы ресурс шрифта, которым span был набран, и
   `page.get_fonts()` перестаёт его отдавать) — извлекается embedded-шрифт
   через `doc.extract_font()`, с сопоставлением имени по
   `get_text("dict")`'s `span['font']` (без subset-префикса) против
   `get_fonts()`'s `basefont` (с префиксом вида `BAAAAA+...`).
4. Уцелевшие (не-PII) слова span'а вставляются обратно через
   `page.insert_text()` тем же шрифтом/размером/базовой линией
   (`span['origin']`). Если у извлечённого шрифта нет рабочей
   Unicode-cmap-таблицы (`fitz.Font(...).has_glyph()` не находит даже
   латиницу — типично для *subset*-шрифтов: PDF адресует глифы напрямую
   по GID, а не через cmap файла, так что своя cmap subset'у просто не
   нужна и часто отсутствует) — используется системный шрифт-fallback
   (`_FALLBACK_FONT_CANDIDATES`: Liberation/DejaVu на Linux, Arial/Times
   на Windows) с проверкой покрытия нужных символов.
5. Отдельно, `padding` (см. `constants.PDF_REDACTION_PADDING`) для
   редакции самого span'а **не применяется** — bbox span'а из
   `get_text("dict")` уже точно охватывает строку по метрикам шрифта, а
   padding на плотно расположенных строках задевал соседний span снизу/
   сверху, стирая его как побочный эффект (тот же класс бага, что и
   пункт выше, только источник — наш собственный отступ). Padding
   по-прежнему применяется только к косметическим чёрным прямоугольникам,
   которые рисуются `page.draw_rect()` поверх уже удалённых из content
   stream PII-слов — это чисто визуальная маркировка, не операция
   редакции, так что расширение прямоугольника ничего не портит.

OCR-путь (изображение, не текстовый слой) этой сложности не касается: там
нет PDF-span'ов, редактируются пиксели напрямую через
`redact_page_boxes`.

### 3. OCR как отдельный источник bbox'ов с общим downstream-кодом
`pdf/ocr.py` инкапсулирует вызов `pytesseract` и приводит его вывод
(`image_to_data`) к тому же виду "слово + bbox + номер страницы", что и
`text_extractor.py` для текстового слоя. Решение о том, какой источник
использовать для страницы, принимается один раз (есть извлекаемый текст
или нет) в `anonymizer.py`; сама детекция и редакция ниже по потоку не
знают, откуда пришли слова.

Движок — `pytesseract` + системный Tesseract (не EasyOCR/PaddleOCR):
- pip-нативные ML-OCR добавили бы вторую тяжёлую модель поверх Natasha
  (~100 МБ) и заметно увеличили бы время холодного старта;
- Tesseract с `rus.traineddata` даёт приемлемое качество для печатного
  текста договоров/сканов, чего достаточно для этой фичи;
- цена — внешняя системная зависимость вне `uv sync`, которую нужно явно
  задокументировать в README и проверять при инициализации (понятная
  ошибка, если бинарник не найден в `PATH`).

### 4. `pdf/` как подпакет, а не плоские файлы
Повторяет структуру `detection/` (`__init__.py` с явным re-export
публичного API, внутренние модули не импортируются напрямую снаружи).
Черновик `feature.md` предлагал плоские `pdf_anonymizer.py` +
`_pdf_renderer.py` — при добавлении `text_extractor.py` и `ocr.py` (нужны
по решениям 1 и 3) это уже 4 файла, что структурно совпадает с мотивацией,
по которой детекция была вынесена в подпакет.

### 5. `PyMuPDF`/`pytesseract` — опциональная группа зависимостей
Основной пайплайн (`config.py`, `pipeline.py`, `llm_proxy.py`) не должен
требовать PyMuPDF/Tesseract для пользователей, которым нужен только
текстовый путь. `pdf/__init__.py` импортирует `fitz`/`pytesseract` лениво
и поднимает собственное исключение с понятным сообщением
(`uv sync --extra pdf`) при отсутствии — по аналогии с тем, как
`NatashaNER` обрабатывает отсутствие своих моделей, но здесь ошибка
поднимается, а не тихо деградирует: обезличивание PDF без реальной
редакции — это не приемлемая деградация (в отличие от "работать только на
регулярках без Natasha" для текстового пайплайна, где частичная детекция
всё ещё полезна).

### 6. URL исключены из редакции по умолчанию
Обнаружилось на реальном документе: ссылка на публичный государственный
реестр (КНМ) нужна читателю обезличенного документа, а не является
угрозой приватности сама по себе — но `entity_types=None` (редактировать
всё найденное) зачёркивал и её наравне с ФИО/телефонами.

`anonymize()` получил `redact_urls: bool = False`. Правило:
- `entity_types` не задан → редактируется всё найденное, **кроме** `URL`,
  если явно не передан `redact_urls=True`;
- `entity_types` задан явно → он приоритетен: если вызывающая сторона
  сама перечислила `"URL"`, ссылки зачёркиваются независимо от
  `redact_urls` (явное намерение важнее общего дефолта).

Альтернатива — заставлять всегда явно перечислять `entity_types` без
`URL`, если ссылки не нужны — отклонена: пользователю пришлось бы
перечислять все остальные типы вручную при каждом вызове, тогда как
"не трогать ссылки" — разумный дефолт для документов, где URL обычно
public-facing (порталы, реестры), а не приватные данные конкретного
человека.

## Риски / Компромиссы

- **[Риск] OCR-ошибки распознавания** (спутанные цифры, "0"↔"O" и т. п.)
  могут привести к тому, что regex/Luhn-валидаторы в `PatternMatcher` не
  сработают на зашумлённом тексте → PII на сканах может остаться
  незамеченной.
  **Митигация**: явно документировать в README, что OCR-путь менее надёжен,
  чем текстовый слой; результат обезличивания (`redacted_by_type`,
  `pages_processed`) позволяет вызывающей стороне заметить страницы с
  подозрительно малым числом найденных PII и направить их на ручную
  проверку. Автоматическая метрика уверенности OCR — открытый вопрос ниже.

- **[Риск] Over-redaction на границе слова.** Bbox слова из
  `get_text("words")`/`image_to_data` может неточно совпадать с границей
  PII-подстроки, если PII — часть более длинного "слова" без пробелов
  (например, "тел.:+79991234567" склеено PyMuPDF в один токен).
  **Митигация**: зачёркивается весь bbox слова, содержащего PII-подстроку
  (не более точная под-область) — это делает редакцию строго
  консервативнее (может зачеркнуть на 1-2 соседних символа больше), но
  никогда не оставляет PII частично видимой. Точность важнее эстетики.

- **[Риск, устранён] Span-level редакция ломала соседний не-PII текст на
  той же строке.** Изначально предполагалось, что редакция по bbox
  отдельного слова достаточно точна и не задевает соседний текст — на
  синтетических тестах так и было. На реальном документе (выравнивание
  по ширине, вся строка — один content-stream span) выяснилось, что
  `apply_redactions()` удаляет текст по границам span'а, а не
  прямоугольника: соседние слова на той же строке пропадали или
  обрезались наполовину, хотя прямоугольник их не касался.
  **Решение**: см. Решение 2 (span-level редакция + восстановление
  текста родным или fallback-шрифтом). Зафиксировано отдельным
  Requirement в spec.md ("Сохранение не-PII текста при редакции").

- **[Риск, принят] Ложные срабатывания слоя детекции (не специфично для
  PDF).** Natasha иногда классифицирует короткие изолированные числа
  (например, день месяца «27» в дате) как ORG. Это баг общего слоя
  `detection/`, воспроизводимый и в текстовом пайплайне — не
  PDF-специфичен и не устраняется в рамках этого change по решению
  пользователя (см. сессию разработки). PDF-модуль просто зачёркивает то,
  что вернул `PIIDetector`, и не пытается компенсировать его ошибки.

- **[Риск] Производительность на больших многостраничных PDF.** OCR
  постранично существенно медленнее текстового извлечения.
  **Митигация**: не в скоупе первой итерации — явно принимается как
  компромисс; при необходимости страницы можно обрабатывать параллельно
  (не меняет публичный контракт).

- **[Риск] Внешняя системная зависимость (Tesseract) усложняет
  установку/деплой** по сравнению с чисто pip-based проектом.
  **Митигация**: `pdf` — опциональный extra, а не обязательная
  зависимость; отсутствие Tesseract не ломает базовый пайплайн, только
  OCR-путь для сканов (см. Решение 5 и соответствующий Requirement в
  spec.md).

## План внедрения

Новая функциональность, обратной несовместимости нет:
1. Добавить extra `pdf` в `pyproject.toml`, бамп версии.
2. Реализовать `pdf/` (text_extractor → ocr → renderer → anonymizer) в
   этом порядке, так как каждый следующий модуль зависит от формата,
   отданного предыдущим.
3. Обновить `__init__.py` пакета с защищённым (lazy) экспортом.
4. Добавить тесты в `tests/` (директории пока нет — создаётся вместе с
   первым тестом, как отмечено в `CLAUDE.md`), включая smoke-тест на
   PDF с текстовым слоем и (если Tesseract доступен в CI) на скан.
5. Обновить README: раздел про установку OCR-зависимости и про то, что
   OCR-путь менее надёжен, чем текстовый.

Отдельного отката не требуется — extra `pdf` ничего не меняет для
существующих пользователей текстового пайплайна, если не установлен.

## Открытые вопросы

- Нужна ли метрика уверенности OCR (`pytesseract` отдаёт confidence на
  слово) в структуре результата, чтобы вызывающая сторона могла
  программно отличить "надёжно обезличено" от "низкая уверенность,
  проверьте вручную"? Не меняет форму requirements в spec.md (там уже
  заложено, что результат сообщает статистику по типам/страницам) —
  решается на уровне полей `PDFAnonymizationResult` при реализации.
- Стоит ли добавить опцию явно исключить сканированные страницы из
  обработки (например, флаг "только текстовый слой, скан — пропустить с
  предупреждением", а не пытаться OCR всегда)? Не влияет на выбранный
  подход (OCR-фолбэк остаётся дефолтом), решается флагом при реализации.
